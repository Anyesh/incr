## [0.2.0-beta.6] - YYYY-MM-DD

### Added

- **Cycles resolve to values.** `create_query_with(f, QueryOpts { cycle })` takes a `CycleStrategy`: `Fallback(g)` lands `g(&Cycle)` for a query on a cycle (`create_query_with_fallback` is the shorthand), and `Fixpoint::new(initial)` iterates the cycle with optional `converged`, `step`, `max_iterations` (default 100) and `on_limit`. Members without a strategy that read each other land `Cyclic`, with an empty slot: `try_get` returns `Err(Cycle)` with the participants, `get` panics with "dependency cycle: ...", and a later `set` that breaks the cycle recomputes them. `cycle_of(h)` names the group a node landed in. A landed group re-verifies as a unit, so an upstream change that cuts off recomputes none of its closures. The landed values do not depend on which member is read first, with two exceptions: a `get` that enters a cycle at a query with no strategy panics during discovery, where `try_get` returns `Err(Cycle)` to the member that read it and lands the same values as any other entry unless a member's closure branches on that error, and membership can differ when reads depend on provisional values.
- **Per-type cycle fallbacks.** `rt.set_cycle_fallback::<T>(g)` sets one fallback for every query of `T` created with `CycleStrategy::TypeFallback`: such a query `q` on a cycle lands `g(&cycle, q)`, as if it had its own `Fallback`, and stores no strategy of its own. Setting a type's fallback twice panics, and so does creating a `TypeFallback` query of a type that has none.
- **Watching nodes.** `rt.watch(h)` reports `h` through `rt.drain_dirtied_watched()` whenever a change moves it off Clean, and `rt.unwatch(h)` stops that and drops its pending report; a node that is neither Clean nor Cyclic when watched is reported at once, and both calls are allowed inside a compute. A drain returns each dirtied node once, as an `ErasedIncr`, in the order the dirty walks found them, and `rt.typed_handle::<T>(e)` turns one back into an `Incr<T>` (`None` unless it names a live node of this runtime whose value type is `T`). In Python, both runtimes have `watch(node)`, `unwatch(node)` and `drain_dirtied_watched()`, which returns `NodeId`s and leaves out nodes deleted since.
- **`NodeTable`: computes find or create their nodes by key.** `rt.create_table::<K, T>()` gives a map from keys to nodes of that runtime: `get_or_insert_input(rt, key, init)`, `get_or_insert_query(rt, key, f)` (and `_with` for a cycle strategy), `get`, `remove` and `for_each`. A compute may call `get_or_insert_*`, which is how it creates nodes now that `create_input` and `create_query` refuse a compute; the lookup is not a dependency, `rt.get` of the handle is. A hit is lock-free; a miss takes the table's mutex, creates the node and publishes it, so racing missers get one node. A deleted entry is a miss. Keys hash with the in-crate `FxBuildHasher` unless `create_table_with_hasher` is given another. `Hash`, `Eq` and `Clone` of a key are value code.
- **`GridTable`: a node table for `(sheet, row, column)` keys.** `rt.create_grid_table::<T>()` has `NodeTable`'s `get_or_insert_input`, `get_or_insert_query`, `get_or_insert_query_with` and `get`, plus `get_or_insert_query_lazy`, which builds the compute and options only on a miss (threads that miss a key together each build, as does a `make` that creates its own key, and every build but the one that creates the node is dropped), with the same hit, miss, deleted-entry and doomed-frame rules, but finds a node by indexing paged per-column arrays instead of hashing: 8 bytes per entry in a used page, and a walk down a column reads adjacent memory. Columns are sparse: a column reaches its 64-row pages through fixed directory levels, so a column holding one node costs about 1.6 to 1.7 KiB whether that node is in row 0 or row 1,048,576, and a dense column about 8 bytes per row. Keys are bounded (`GridKey::SHEETS`, `ROWS`, `COLUMNS`) so a stray key cannot allocate a huge directory. Outside a compute, `insert_inputs(rt, entries)` and `insert_queries_watched(rt, entries)` create a batch of nodes under one hold of the runtime lock, the latter watching each, and hold no copy of the batch while they do. A batch with a key that is out of range, repeats or has a live node panics and creates nothing, leaving every key of the batch free for a later insert; a panic partway through creating the nodes frees every key whose node it had not yet entered. incr-compute and incr-concurrent export it as `GridTable<T>`. <!-- figures measured on incr d39869d (built-notes-final/spreadsheet-grade.md, grid table layout): a column 1600 B for one node at row 0 and 1704 B at row 1<<20, a dense column 8.13 B per row in incr-core's grid_memory test -->
- **Owned children.** Inside a compute, `rt.child_input(key, init)`, `rt.child_query(key, f)` and `rt.child_query_with(key, f, opts)` return the compute's child named `key` (by key, key type, value type and kind), created and owned by the computing node on the first call and returned unchanged on every later run; on a hit `init` or `f` is dropped unrun, since a child is never updated by its creator. A Clean landing of the creator deletes the children its run did not ask for, keeping any that another node still reads or that is busy, which are checked again at the next Clean landing. A landing that discards the run (a panic, a cycle or wound unwind, a dep deleted under it) deletes the children that run created and never hands them out again. Deleting the creator deletes its children and theirs. The calls panic outside a compute. `Drop` of a deleted child's closure, value or key runs after the creator lands.
- `rt.set_placeholder::<T>(v)` sets the value a pending handle of type `T` reads. A table miss in a doomed frame returns a pending handle instead of creating a node; it reads the placeholder inside that frame and panics anywhere else.
- **Deep chains replay instead of overflowing the stack.** A query created with `QueryOpts { replay: Replay::Allowed, .. }` whose read would nest past the frame budget (`rt.set_max_frames(n)`, 256 by default and 32 in debug builds, whose frames are larger, or the `INCR_MAX_DEPTH` environment variable) gets its type's placeholder instead, and the closure runs on: under `Local` to its end; under `Shared` its further reads of its own runtime's queries that are not Clean take placeholders too, and its first other engine call (see Changed) ends the run there with an engine unwind, which a `catch_unwind` around that call catches and the closure's next read or `set` raises again (a read from a destructor that unwind runs takes the placeholder). Either way its frame and the frames below it that can take one are discarded, and a driver computes the node that read wanted at a shallow depth and runs them again from the bottom. `rt.set_max_stack_bytes(n)` adds an optional budget on the stack used since the thread's outermost engine call, for frames whose size the frame count does not bound. A type with no placeholder, and a query left at `Replay::Native`, nest as before. Results, cycle outcomes and panics included, are those of the unbounded run apart from the cases under Known limitations below, and on one thread a replayed read that panics raises the payload the unbounded run raises: in a release build a 100k-deep first compute runs on a 1 MiB thread, each node computing at most twice. Any query's closure may run more than once for one read (a retry, a wound, a cycle's iterations, and now replay), so it must be pure, and a replayable one must not panic or loop on a placeholder. A `Replay::Native` query that a replaying closure reads may be computed ahead of need, at most once per revision. That run lands nothing: a later read of the query in the same revision takes the value or panic it ended with, and the children it created, if nothing it read has changed. Otherwise the later read runs the closure again, and so it does when the run kept nothing: it read a dep that did not land Clean or a panic that another such run kept, it read through a run that kept nothing, or it met a cycle. Under the default budget of 256 a deep chain's reads use about 1.6 to 2.7 KB of stack per level (release, `Shared`: a median of 2,176 bytes on a cycle with a fallback strategy, 1,616 with `Fixpoint`) and peak at about 0.56 MB; code that raises or disables the frame budget needs a thread stack sized for its depth at that rate. <!-- stack figures: worker-10 probe w10_stack_per_level (refs c9618229) on t10 562ebeed, row T10-trainB-tsan-stack-256; the figures are the 73362faa-370c46 run in the last comment; the 100k-deep first compute on a 1 MiB thread with at most two runs per node is asserted by the release tests local_chain_100k_on_a_1_mib_thread and shared_chain_100k_on_a_1_mib_thread --> <!-- pending: the Local/Shared split lands with w/T10-doom-placeholder-unwind, final train --> <!-- figures from release-figures gh-cmd 73362faa-370c46 (rerun.sh on release 8e1a2f8ab, runner 1000018649, 3 rounds; ranges over rounds) -->
- **Python: `CycleError`.** A read that closes a cycle with no value raises `incr.CycleError` (`incr_concurrent.CycleError`), a `RuntimeError` subclass whose `args` are the message and the participants' node ids. An engine unwind that crosses a Python callback is carried through it as that exception and resumed unchanged, so a callback that catches it gets the result `try_get` would give. A read in a query's `finally` that a cycle runs is an ordinary read: it returns its node's value or raises that node's own exception, and the cycle goes on to raise `CycleError` at the top-level read. <!-- folded from Changed (integrator ruling (c), 28 Oct: beta.5's bindings have no CycleError, so this is part of the feature, not a fix): on a b9f0d0bf3 wheel the top-level read raised the finally read's ValueError instead (test_compute_in_finally_keeps_its_outcome_and_the_cycle[get-get-raises], local and concurrent, test_new_api.py:330, gh-cmd d1838076-bbe78d); the release branch passes all 24 variants of it and test_clean_read_in_finally_keeps_the_cycle_error (gh-cmd d1838076-094c2e); rows T11-fix-unwind-stash, T11-unwind-nested-raise -->
- **Python: cycle strategies, tables, children and replay.** `try_get` (on `Runtime` and on the `RuntimeRef` a query receives) returns the value or raises `CycleError` as an ordinary exception a query may catch. `create_query(f, fallback=g)` lands `g(ids)` for a query on a cycle, and `create_query(f, fixpoint=Fixpoint(initial, converged=, step=, max_iterations=, on_limit=))` iterates it; `replay=True` makes it replayable, with `Runtime.set_placeholder(v)` (once per runtime, since every Python value shares one type), `set_max_frames(n)` and `set_max_stack_bytes(n)`. `Runtime.create_table()` returns a `NodeTable` with `get_or_insert_input(key, init)`, `get_or_insert_query(key, f, ...)`, `get`, `remove` (`KeyError` when absent) and `items()`; a key's `__eq__` or `__hash__` that calls into incr raises the contract error. Inside a query, `child_input(key, init)` and `child_query(key, f, ...)` return its owned children.
- **Python: no persistent memoization in this release.** `MemoTable` has no Python binding: incr-persist has no Python bindings at all, and caching Python values in files would need a serialization contract that is safe to load from a cache file, which `pickle` is not.
- **Collection operators on a cycle land the values a fresh operator would.** A `filter`, `map`, `aggregate`, `join` or sorted operator whose user function read a cycle's provisional value, or that ran as a member of a cycle's episode, rebuilds from its upstream snapshot on its next run, so deltas applied against a provisional value never survive the landing. A `group_by` router refuses a provisional value with the cycle (`Err(Cycle)` from `try_get`, a panic from `get`) and routes nothing.
- On wasm with `panic = abort`, a cycle whose members all have a strategy resolves without unwinding. A `get` that closes a cycle with no value, a nested cycle that would reach an outer `try_get` as `Err`, and a wound under a threaded `Shared` runtime rely on unwinding and abort there.
- **Debug builds check the lock order.** Every incr lock (the runtime's state, table misses, arenas, collection operator state and logs, the watch queue, and incr-persist's Store mutex and dependency index) has a place in one global order, and a debug build panics when a thread takes them out of order, or waits on a node claim, starts a compute or runs a `filter`, `map`, `aggregate` lift, `join`, `group_by` or sort key function while it holds a lock that a claim holder may request. The few locks no claim holder requests, such as incr-persist's Store mutex, are allowed there. This also catches a backend or subscriber that drives another `Store` on the thread that holds the first one's mutex. Release builds check nothing.
- **incr-persist: persistent memoization.** `MemoBuilder::table(name, version)` declares a table and `define(table, f)` gives it a closure `Fn(&MemoCtx, &K) -> T`; `open(&store, backend)` opens a `Memo` over a `Store` and a memo backend (`FileMemo`, `SqliteMemo` or `MemoryMemo`). `memo.get_or_insert(table, key)` (`ctx.get` inside a closure) restores a missed entry from the last checkpoint with its value and deps: it verifies without running while its store inputs, collections and externals keep their fingerprints, and otherwise runs once and cuts off if its value is unchanged. `memo.checkpoint()` writes every live entry whose deps all map, and `MemoOptions::auto_checkpoint_secs` runs it on a thread under `Shared`. Entries are dropped whole when the `BuildId` (`CurrentExe` on Linux and Android, or `Fixed`) or the salt changes, and per table when its name, version or key and value types do. `memo.set_external(name, fp)` and `ctx.external(name)` cover state the store doesn't hold, and `memo.stats()` counts reuse, reruns, cold restores and corrupt frames.

### Changed

- **Deleting a node that owns nodes claims the whole set at once.** A strict delete of an owner (`delete_node`, `try_delete_node`) gathers it and everything it owns, refuses if any of them has a dependent outside that set (edges inside it no longer count, so an owner may read what it owns), and claims every member under one hold, or none: a member being computed, set or deleted elsewhere rolls the claim back, and the delete waits for it and retries. Two deletes of overlapping owned trees no longer wait on each other forever. Deleting an owner inside a compute now panics. `delete_with_dependents` deletes such sets together, and nodes whose dependents lead back to each other (a dependency cycle, or owners that read each other's nodes) are deleted together instead of looping. <!-- on main since beta.5 (integrator ruling 28 Oct 07:23, no intended-changes entry): main commit 59e40ec14 (owned-set claim, runtime_claim_set.rs), with 43c5f2759 (one write hold) and 15f609fba (waits for a set's claim); line from 8a8820f84; the line makes no beta.5 claim -->

- **Contract change: value and key methods may read Clean nodes and must not otherwise call into the runtime.** A `Clone`, `PartialEq`, `Hash`, `Eq` or `Ord` that the runtime calls on a value, a collection element or a key may `get` a Clean node, an input another thread is setting included (it reads the old or the new value), and that read takes no lock and never waits. - **A panic in a dep a node stopped reading no longer fails its read.** Before rerunning a Dirty node, the walk recomputes every dep the node recorded last time, and a panic in one that the rerun would not read no longer fails the read: `if get(sel) == 0 { get(f) } else { 100 }` returns 100 once `sel` is 1, even after `f` starts panicking. ## [0.2.0-beta.5] - 2026-10-16

### Added

- **`incr-persist`, a new opt-in crate for durable, shareable state.** A `Store` keeps a runtime's inputs and collections in sync with an ordered operation log held by a pluggable `Backend`, and incr-core gains no serde dependency. It ships three backends: memory (several stores in one process, for tests), file (single writer and many readers, torn-tail recovery, crash-safe compaction) and SQLite behind the `sqlite` feature (many writers across processes, WAL mode). A conformance suite behind `backend-tests` holds any backend, including your own, to the same contract.
  - `store.input(key, default)` and `store.collection(key)` declare persisted keys; the first declaration in the log wins, so every process agrees on defaults. `restored_keys(prefix)` lists keys known from the log that this process has not declared yet.
  - `set`, collection `insert`/`delete`/`replace` and `batch` append to the log before applying, with `Durability::Sync` (the default) or `Buffered`. An error after the append poisons the store until it is reopened, so a retry can never double-apply.
  - `checkpoint` compacts the log, forgetting keys that are back at their default; `refresh` applies other writers' records, and a store that fell behind a compaction catches up from the snapshot while user queries over its keys survive.
  - `store.delete(key)` resets a key for every process, `store.undeclare(key)` removes it from this process's graph only, and `subscribe` reports every applied record in log order with its origin.
  - Debug builds report a write that bypassed the store through a raw handle.
- **Cascading delete and erased handles in incr-core.** `ErasedIncr` names a node of any value type; `delete_with_dependents` removes a node and everything that computed against it or is owned by it, returning the count; `is_alive` checks a handle without panicking; `try_delete_node` is a strict delete that returns `DeleteError::{HasDependents, NotAlive}` instead of panicking. All three are in the Python bindings too.
- An example, `examples/persist-config`, whose test kills a writer with SIGKILL mid-write sixteen times and checks that every acknowledged write survives each restart.

### Changed

- **Contract change: `group_by` owns its group nodes.** Deleting a `group_by` router now releases its groups too, and panics with "still has dependents" if any group has consumers (delete those first, or use `delete_with_dependents`). Before, the delete succeeded and leaked the groups. After a router is deleted, every `IncrCollection` in its `GroupedCollection` is stale.
- `get` and `set` find a node's value arena by the type tag the node already stores instead of hashing its `TypeId`, so propagation runs 9 to 12% fewer instructions under `Local` and 5 to 8% fewer under `Shared`.
- Deleting a node drops its compute closure and observers after releasing the runtime lock, so a `Drop` that touches the runtime no longer deadlocks `Shared` or double-borrows `Local`.

### Fixed

- `delete_node` could claim the next occupant of a slot that another thread deleted and recycled between its state check and its claim.
- In Python, each read of a collection's `.version_node` created a new node that was never freed; every collection now shares one, and `NodeId` compares and hashes by node identity.

## [0.2.0-beta.4] - 2026-10-16

### Soundness

Seven races in the `Shared` protocol, all present in 0.2.0-beta.3, are fixed. Each one has a deterministic test that parks a thread at a named point in the protocol, and loom models now run the real runtime over every interleaving up to a preemption bound, in CI on every push.

- **A delete could remove a node that a compute had just started depending on (B1).** `delete_node` checked for dependents and claimed the node in two steps, so a publish could land between them and its edge was dropped. Both now happen under one lock hold.
- **A compute that raced a delete could add a reverse edge to the recycled slot's next occupant (B2).** Recorded deps now carry the slot's generation and are validated under the publish lock, and a compute that read a deleted dep discards its value and runs again.
- **A dep read for the first time could miss a concurrent `set` (B3).** Its reverse edge did not exist until publish, so the set's walk could not reach the reader. A publish that finds a new dep changed since the read now lands the node `Dirty`.
- **An early-cutoff compute flagged mid-flight could strand its dependents (B4), and red/green verification could verify a node `Clean` past a concurrent `set` (B5).** Both left a node `Clean` over a `Dirty` dep, returning a stale value forever. Verification now claims the node and treats a dep that is not `Clean` as changed, and a compute that read a dep landing non-`Clean` lands `Dirty` itself.
- **`verified_at` could name a revision whose dirty walk had not run yet (B6).** It now uses a walked-revision watermark that only passes revisions whose walks have finished.
- **A compute could stamp a change below the `set` that caused it (B7).** Its revisions were captured before its claim, and the claim can succeed on a later `Dirty` than the one it observed. The loom models found this one.
- The dirty walk passes through `New` nodes, so a `Failed` dependent behind a node recovering from a stale dep still recovers, and a panicking compute whose new dep had a change in flight lands `Dirty` rather than staying `Failed` with no walk left to wake it.

### Changed

- Readers of a `Dirty` node now wait while another thread verifies it, as they already did during a recompute.
- Propagation runs fewer instructions per `set` and `get` than 0.2.0-beta.3, 8 to 11% fewer on `Local` chains and 2 to 6% fewer on `Shared`, because a compute whose deps did not change now publishes without allocating. `Shared` also gains atomic read-modify-writes in verification and in the dirty walk, whose cost shows up in cycles rather than instructions.
- **Breaking for custom strategies and dep stacks.** `Cells` gains `DepListCell`, `Watermark`, `new_watermark`, `walked`, `complete_walk`, `fence_seqcst` and a defaulted `backoff`. `DepStack::record_dep` takes the dep's generation, `pop_frame` returns a `PoppedFrame` carrying a poison flag, and `DepStack` gains `poison_current_frame`. Code that only uses `Local` or `Shared` is unaffected.

## [0.2.0-beta.2] — 2026-06-12

### Soundness

A full audit of the Shared protocol found and fixed undefined behavior that Miri's race detector confirms on beta.1:

- **Value storage is now tear-free under concurrency.** Shared value slots are hazard-pointer-protected pointer swaps instead of in-place `UnsafeCell` writes; a `get` racing a `set` (or a recompute) on the same node was a data race on heap values, with use-after-free potential. Local keeps in-place storage and got faster (RefCell + inline slots replace an RwLock + Box indirection).
- **Every state transition is a CAS.** The verified-clean path could clobber another thread's `Computing` claim and run two computes on one node; claim losers now wait for the owner instead of reading stale or empty slots (two threads racing the first `get` of a query could read an uninitialized slot).
- **A `set` racing an in-flight compute can no longer be swallowed.** A new `ComputingDirty` state plus pending-marker `changed_at` stamping and compute-start-revision `fetch_max` stamps close several stale-forever windows; revision bumps are atomic (two concurrent `set` calls could collapse into one revision).
- **Compute closures have a panic boundary.** A panicking closure lands its node in `Failed` (previously: wedged in `Computing` forever, deadlocking all future readers), keeps the runtime usable, and recovers when a dependency changes. Lock poisoning is no longer fatal; operators stage user-closure results outside locks so an unwind cannot half-apply a batch.
- **Dependency cycles panic with a diagnostic** instead of hanging or overflowing the stack. (Known limitation: a cycle spanning two threads' in-flight computes livelocks; cross-thread cycle detection needs a waits-for graph.)
- **Foreign-runtime and stale handles are rejected in release builds** (was: debug_assert only; release silently corrupted whichever node shared the slot).
- **Python collections no longer dangle.** They held a raw pointer into the runtime object; dropping the runtime first left use-after-free on `insert`. They now hold strong references.

### Added

- **`delete_node`**: nodes can be deleted (leaves first); slots and arena storage recycle under a bumped generation, so long-lived dynamic graphs no longer grow without bound. Stale handles panic with a clear message.
- **`aggregate` operator**: incrementally maintained monoid fold over a balanced aggregation tree, O(log n) per change, correct for non-invertible folds (max, min). `reduce` keeps snapshot semantics for arbitrary folds and says so in its docs.
- **Incremental `pairwise`/`window`**: consume positional sort deltas; one upstream row produces O(1) / O(size) output deltas instead of a full rebuild.
- **Observers**: `observe(handle, callback)` + `stabilize()` for batch change notifications on the pull model; `unobserve` to detach.
- **Delta-log compaction**: collection logs drop the prefix all registered consumers have passed (everything, if no consumer is attached); operators attached to populated collections bootstrap from a snapshot. Log memory is bounded by consumer lag, not collection lifetime.
- **Queries may read any number of inputs** (was: panic above 255 dependencies).
- **In-repo Salsa comparison harness** (`crates/incr-bench`): the README's numbers are reproducible with `cargo bench -p incr-bench --bench salsa_compare`.
- **ThreadSanitizer CI job** and a mixed-workload concurrent stress suite; Miri runs the threaded hammer tests.
- **Python**: real exception propagation (callbacks re-raise the original Python exception), `delete_node`/`observe`/`stabilize`/`aggregate` bindings, abi3 wheels for CPython 3.10+, pytest suite wired into CI on 3.10 and 3.14. The `incr_concurrent` classes are genuinely shareable across Python threads and release the GIL around computing calls (was: everything `unsendable`, defeating the crate's purpose).

### Changed

- Collections use the strategy lock: single-threaded users no longer pay RwLock acquires per collection op.
- Shared `get` costs two hazard-pointer atomics per value read and Shared writes allocate (the price of tear-free lock-free reads); chain propagation is ~108 ns/node Local, ~348 ns/node Shared on the bench machine. beta.1's faster Shared numbers were measured on the racy code.
- pyo3 0.23 → 0.26; Python floor is now 3.10.
- Workspace version is centralized; release publishing verifies crates (no `--no-verify`) and ships sdists + abi3 wheels.

## [0.2.0-beta.1] — 2026-05-20

### Architecture

The big break: `incr-compute` and `incr-concurrent` are now thin re-export wrappers over a shared engine crate, `incr-core`. The engine is parameterized over a `Cells` strategy trait (`Local` for single-threaded, `Shared` for `Send + Sync`); the compiler monomorphizes each surface crate into the appropriate variant. The full algorithm — dependency tracking, ensure_clean's iterative post-order walker, red-green early cutoff, the segmented node store, the typed value arenas, all nine operators — lives in one place. v0.1's parallel implementations are deleted.

### Breaking changes

- **`Value` bound** is now `Clone + PartialEq + Send + Sync + 'static` in **both** crates (was `Any + Clone + PartialEq + 'static` in `incr-compute` v0.1). Most user types already meet the bound; types that don't will need wrapping (e.g., `Arc<Mutex<T>>` instead of bare `Rc<...>`).
- **Single `Runtime` per crate** rather than the v0.1 split. `incr_compute::Runtime` is `Runtime<Local>`; `incr_concurrent::Runtime` is `Runtime<Shared>`. The public method names match v0.1.
- **`NodeId::raw()` → `NodeId.0`**. The struct is `pub struct NodeId(pub u32)`; the field is accessed directly.
- **`Incr<T>::node_id()` → `Incr<T>::slot()`**. The handle returns its u32 slot index.
- **`IncrCollection::version_node_id()` removed**. Use `version_node()` which returns `Incr<u64>`.
- **`count()` returns `Incr<u64>`** (was `Incr<usize>` in `incr-concurrent` v0.1). Sized to the network-portable type.
- **`Runtime::set_label`** takes a `u32` slot directly (was `NodeId` in v0.1).
- **`Runtime::set_tracing` removed**. `get_traced` now arms tracing internally for the duration of the call.
- **`SortedCollection::entries()` → `snapshot()`**.
- **`IncrCollection::delete` returns `bool`** indicating whether a delete was actually recorded (was: silently dropped the inner result in production v0.1).
- **`Runtime::set` on a query node panics** with a clear message. This was undefined behavior in v0.1 (would overwrite the arena slot and corrupt the state machine).
- **`Runtime` `!Send + !Sync` under Local**; `Send + Sync` under Shared (was: mixed in v0.1).

### Added

- **`incr-core` published crate** as the shared engine. Re-exported types include `Cells`, `Local`, `Shared`, `PtrCell`, `Lock`, `DepStack`, `LocalDepStack`, `SharedDepStack`, `LocalLock`. Users who want to build a custom concurrency strategy on top of the engine can do so.
- **Overflow-dep storage**: queries with more than 7 dependencies are now supported (was: hard limit of 7 in v0.1's inline-only path). Overflow lists live in a heap-allocated `DepList`, reclaimed via the [`haphazard`](https://crates.io/crates/haphazard) global hazard-pointer domain. Concurrent readers hold a hazard pointer during traversal; writers retire displaced lists for deferred free.
- **Real per-node tracing** in `get_traced`: every node visit during a get records a `NodeTrace` (`VerifiedClean` or `Recomputed { value_changed }`). Aggregates (`nodes_recomputed`, `nodes_cutoff`) populated from the trace. Hot-path cost: one Relaxed u8 load per compute when disarmed (~1 ns).
- **Property tests under both strategies**: the same generator + verifier (`verify_incremental_matches_batch<C: Cells>`) runs against `Local` and `Shared`. 1000 random function graphs × 2 strategies + 500 random collection op sequences × 6 tests = ~5000 random scenarios per `cargo test` run.
- **Concurrent stress test** for `incr-concurrent`: 4 reader threads + 1 writer thread × 1000 iterations with torn-read detection.
- **Miri validation**: `cargo +nightly miri test -p incr-core --lib` covers all unsafe paths (segmented store, hazard-pointer reclamation, state machine CAS races). Zero undefined behavior reported across 79 unit tests.
- **`Runtime::graph_snapshot`** returns real per-node `NodeInfo` with dependencies (read from inline-7 + overflow storage) and dependents (from inner state).
